# FAH-Extraktor: MikroTik-Integration – Kurzspezifikation (10.10.2026)

**Ziel:** Ein RouterOS-Backup (`.backup`, `.rsc`) im Browser lesen (Baum mit Rubriken,
Datensätzen, Feldern, Hex) und als Cloud Hosted Router (CHR) virtuell öffnen – WebFig im
Fenster der App, bevor das Backup auf ein Gerät gespielt wird. Gleichzeitig wurde die App von
„UniFi Backup Explorer“ in **FAH-Extraktor** umbenannt (Kachelübersicht je Hersteller).

**Entscheidungen (Betreiber):** echter CHR unter QEMU/KVM als Wegwerf-Sandbox; ein Lauf je
Konto, `VORSCHAU_MAX` zählt UniFi und MikroTik zusammen; Stufe 1 bewusst eng (nur
unverschlüsselte `.backup` mit RouterOS 7, `.rsc` als Beta); einfache Bedienung, jede
Einstellung mit ein bis zwei Sätzen erklärt. Die Netzarchitektur stammt aus dem NAS-Vorversuch
vom 10.10. (verbindlich, siehe Abschnitt 5).

## 1. Was bleibt, was sich ändert
- Bleibt: NAS-Ordner `/volume3/docker/unifi-extraktor`, Compose-Projekt, Containernamen
  `unifi-backup-explorer(-api)`, Port (`.env` `WEB_PORT`), Präfix `/_explorer/`, Cookie
  `fah_explorer`, Label `fah.unifi-vorschau`, Env `VORSCHAU_*`, Deploy-Weg (ZIP + `manage.sh update`).
- Neu: Name „FAH-Extraktor“, Paket `fah-extraktor`, ZIP `fah-extraktor.zip` (`DEPLOY_GLOB` kennt
  dazu die alten Muster), Favicon/Mark „F“, Kachelübersicht als erste Ansicht nach der Anmeldung,
  Vorschau-Fenster (iframe) statt nur „Neuer Tab“, Hex-Rohdaten auch bei UniFi.

## 2. Architektur
```
Browser ──nginx(:80)──► /, /index.html, /_explorer/anmeldung, /favicon.svg, /_explorer/assets/ (statisch, auth_request, sicherheit.inc)
                    └─► /_explorer/api/*  ──► Node-Backend (:3000): Konten · Einstellungen · Vorschau-API · MikroTik-Versionen
                    └─► alles andere (/manage,/api,/wss | /webfig,/jsproxy,/rest) ──► Backend-Proxy ──► Lauf des Kontos
Backend ──Docker-Socket──► Netz unifi-vorschau (internal) ──► UniFi: app+db-Container (https :8443)
                                                           └─► MikroTik: unifi-vorschau-chr-<id> (Alpine+QEMU/KVM, Relay :80 → WebFig)
Backend ──► /cache (Volume fah-chr-cache): chr-<v>.img, lädt bei Bedarf von download.mikrotik.com
```
- Der Catch-all braucht keine Pfadweiche: Der Lauf des Kontos bestimmt `ziel = {host, port, schema}`
  (`unifi`: `app:8443/https`, `mikrotik`: `chr:80/http`).
- WebFig/UniFi laufen als Fenster IN der App: `#vorschau-fenster` (fixed unter dem Header) mit
  `<iframe src="/_explorer/api/vorschau/oeffnen?eingebettet=1">`. Same-Origin; `sicherheit.inc`
  (`frame-ancestors 'none'`) hängt nur an den statischen Explorer-Seiten. Der Proxy streicht
  `x-frame-options` und setzt in jeder Proxy-Antwort `content-security-policy: frame-ancestors 'self'`
  (vorhandene Direktive ersetzen, sonst anhängen).
- Parser laufen im Browser: `src/mikrotik-backup.js` (Decoder des Binärformats) und
  `src/mikrotik.js` (Hülle: `.backup`/`.rsc` → gleiche Grundform wie `openBackup`, `hexDump`).
- Das Backend-Image kopiert das ganze `src/` (Parser werden auch serverseitig gebraucht) und
  `server/` inklusive `server/arten/`.

## 3. Datenflüsse
1. Anmeldung → `/` → `#kacheln`. Kachel → `#drop` mit passendem `accept` → `load(file)` →
   `integration === 'unifi' ? openBackup : oeffneMikrotik` → `#workspace`.
2. MikroTik „Virtualisieren“: `GET /_explorer/api/mikrotik/vorbereitung?hauptversion=7[&mindestens=7.22]`
   → Dialogkarte → `POST /_explorer/api/vorschau?art=mikrotik` (Body = Rohdatei, `X-Backup-Name`,
   `X-Vorschau-Optionen`) → 202 → Polling `GET /_explorer/api/vorschau` (1,5 s laufend / 10 s)
   → `bereit` → Fenster. Der Dialog wird vom Polling nicht überschrieben (nur `#chr-belegt` wird
   nachgeführt), getippte Werte bleiben.
3. Backend-Lauf: Optionen prüfen → CHR-Image im Cache sicherstellen (Download + Entpacken,
   Fortschritt in `schritte[laden].detail`, nur alle ≥ 2 % neu) → Container mit Volume (ro) und
   `/dev/kvm` erstellen → Tar (`auftrag.json` + `kunde.backup|kunde.rsc`, Modus 0600) per
   `PUT /containers/{id}/archive?path=/auftrag` → starten → Logs folgen (Marker `FAH-SCHRITT`,
   `FAH-INFO`, `FAH-BEREIT`, `FAH-FEHLER`, bei Fehlern bis 40 maskierte `FAH-KONSOLE`-Zeilen)
   → eigener Test `GET http://<chr>:80/webfig/` = 200 → `phase = 'bereit'`.
4. Proxy: Browser → Sitzung → Lauf → `leiteWeiter` (http für mikrotik, https für unifi) →
   `aktivitaet(lauf)`. Leerlauf 30 min ohne Proxy-Anfrage, Höchstdauer 8 h (wie UniFi).
   Ob der zusätzliche `POST /vorschau/puls` (alle 5 min aus dem Fenster) nötig ist, klärt der
   NAS-Test: WebFig pollt über `/jsproxy`, jede Proxy-Anfrage zählt bereits als Aktivität.
5. Standard-Zugang MikroTik: Admin setzt `PUT /_explorer/api/einstellungen {mikrotikZugang:{benutzer,passwort}}`
   → `daten/einstellungen.json` (0600, nie im Code). `registrierung` wird dabei nur geändert, wenn
   das Feld mitgeschickt wird. Jedes angemeldete Konto erhält die Vorbelegung über
   `GET /mikrotik/vorbereitung` (bewusste Betreiber-Entscheidung; `daten/` ist auf dem NAS per
   ACL lesbar – im README dokumentiert).

## 4. API-Routen (unter /_explorer/api; Nicht-GET braucht `X-Explorer: 1`; Sitzung Pflicht außer gesund/pruefen/anmeldung/anmelden/registrieren/abmelden)
| Methode/Pfad | Anfrage | Antwort |
|---|---|---|
| `GET /vorschau` | – | Status (unten) |
| `POST /vorschau?art=unifi\|mikrotik` (ohne `art` = unifi) | Body roh ≤ 300 MB; `X-Backup-Name` (percent-kodiert); mikrotik: `X-Vorschau-Optionen` = percent-kodiertes JSON `{dateiart:'backup'\|'rsc', chrVersion:'7.24.5', benutzer, passwort, zugang:{modus:'lokal'\|'wan', ip, prefix}, ports?:[{defaultName}]}` | 202 Status; 400 bei ungültigen Optionen (`{fehler}`); 409 voll (wie heute) |
| `DELETE /vorschau[?id=]` | – | 200 Status (fremde nur Admin → 403) |
| `GET /vorschau/oeffnen[?eingebettet=1]` | – | unifi: 302 + `unifises`-Cookie → `/manage/<site>/dashboard`; mikrotik: 302 → `/webfig/`; kein bereiter Lauf: ohne `eingebettet` 302 `/`, mit `eingebettet` (oder `Sec-Fetch-Dest: iframe`) 200 HTML „Keine virtuelle Vorschau aktiv“ ohne Link |
| `POST /vorschau/puls` | – | 204 (auch ohne eigenen Lauf); setzt `letzteAktivitaet` |
| `GET /mikrotik/vorbereitung?hauptversion=7[&mindestens=7.22]` | – | `{vorschlag, hinweis:string\|null, kanaele:[{kanal,version,zeit}], lokal:[…], quelle:'upgrade.mikrotik.com'\|'cache', stand, zugang:{benutzer,passwort}, image:boolean, kvm:null, max, belegt}` |
| `GET /einstellungen` (admin) | – | `{registrierung, mikrotikZugang:{benutzer,passwort}}` (`GET /benutzer` liefert das Gleiche zusätzlich zur Liste) |
| `PUT /einstellungen` (admin) | `{registrierung?}` und/oder `{mikrotikZugang:{benutzer,passwort}}` | 200 Gesamtstand wie GET |

Status-JSON (gemeinsam, abwärtskompatibel): `{aktiv, id, art:'unifi'|'mikrotik', name, gestartetVon,
phase, schritte:[{key,text,status,detail}], fehler:{text,log}|null, gestartet, bereitSeit, offeneSockets,
zugang:{benutzer,passwort,hinweis}|null (nur bereit), max, andere:[{id,art,name,gestartetVon,phase,
gestartet,letzteAktivitaet,offeneSockets}], leerlaufMin, hoechstdauerStd, jetzt, zuletzt:{name,art,grund,zeit}|null}`
plus je Art: unifi `version:{backup,controller,angeglichen}, sites, geraete, startSite`; mikrotik
`mikrotik:{identitaet, routerosVersion, chrVersion, modus, zugangIp, wwwPort, traeger, kvm, hinweise:[]}`.
Schritt-Keys bleiben `vorbereiten, laden, starten, einspielen, anmelden` (Texte je Art).
Passwörter stehen nie in `andere`, `kurz`, Logs oder Fehlertexten.

Validierung der Optionen (`optionenPruefen`): `benutzer` `/^[A-Za-z0-9._@-]{1,64}$/` (kein `+`,
kein Leerzeichen – `+` ist eine Konsolen-Login-Option), Passwörter ≤ 128 Zeichen ohne
Steuerzeichen; im Konsolenbefehl werden `\`, `"` und `$` escapt (RouterOS-Strings interpolieren
`$`). `chrVersion` `/^\d+\.\d+(\.\d+)?(rc\d+|beta\d+)?$/`, Hauptversion 6 wird abgelehnt.
Verschlüsselte Magic (`0x7291A8EF` RC4, `0x7391A8EF` AES) → 400 mit Hinweis `dont-encrypt=yes`.
Keine Nutzereingabe landet in `containerErstellen` (Image, Binds, Env, Devices nur aus Konstanten).

## 5. Container-Aufbau (belegt im NAS-Vorversuch 10.10.)
- Image `fah-extraktor-chr` aus `chr/Dockerfile.chr` (Kontext `chr/`): `alpine` + `qemu-system-x86_64`,
  `qemu-img`, `python3`, `py3-pexpect`, `mtools`/`dosfstools`; `chr_lauf.py`; `RUN mkdir -p /auftrag /tmp/fah-chr`
  (das Archiv-Ziel muss existieren). Baut `manage.sh` vor `compose build` (Fehler → alte Version läuft weiter).
- Container je Lauf: Name `unifi-vorschau-chr-<id>`, Labels `fah.unifi-vorschau=1`, `.lauf=<id>`,
  `.art=mikrotik`, Env ohne Geheimnisse (`AUFTRAG=/auftrag/auftrag.json`, `TZ`), `NetworkMode unifi-vorschau`,
  `CpuShares 256`, `NanoCpus 1e9`, `Memory 768 MiB`, `Devices /dev/kvm`, `Binds fah-chr-cache:/cache:ro`.
  Scheitert das Erstellen am Gerät → ohne `Devices` erneut, `kvm=false` (QEMU `-accel tcg`,
  Zeitlimits ×3, Hinweis „ohne KVM – deutlich langsamer“). Kein Port-Mapping.
- `auftrag.json` nur in der Schreibschicht; `chr_lauf.py` liest es und löscht es sofort, nach der
  Zustellung auch `/auftrag/kunde.*`. Overlay-Platte `/tmp/fah-chr/platte.qcow2` (qcow2 über
  `/cache/chr-<v>.img`, `-F raw`) verschwindet mit dem Container (`force+v` löscht keine benannten Volumes).
- **Zustellung des Backups: FAT-Platte.** `mformat`/`mcopy` bauen eine FAT32-Image-Datei ohne
  Partitionstabelle mit `kunde.backup`; als zweite virtio-Platte hängt RouterOS 7.24.5 und 7.16.2 sie
  selbst ein (Slot `pcie1`, Datei `pcie1/kunde.backup`) → `/system backup load name=pcie1/kunde.backup password=""`.
  Kein Netz für die Zustellung, kein `guestfwd`, kein HTTP-Server.
- **QEMU:** `-enable-kvm -cpu host` (bzw. `-accel tcg -cpu qemu64`) `-m 384 -smp 1 -display none -vga none
  -parallel none -chardev stdio,id=ser0,signal=off -serial chardev:ser0 -monitor unix:/tmp/fah-chr/mon.sock,server,nowait
  -boot c -drive file=platte.qcow2,if=virtio,format=qcow2,cache=unsafe -drive file=fat.img,if=virtio,format=raw`.
  NIC 1 = Verwaltung: `-netdev user,id=mg,net=<Netz der Zugangs-IP>,host=<Gegenstelle>,dhcpstart=<frei>,ipv6=off,restrict=on`
  + `-device virtio-net-pci,netdev=mg,mac=02:FA:48:00:00:01,romfile=`; je Kundenport (MACs aus `net/devices`)
  `-netdev hubport,id=hN,hubid=N -device virtio-net-pci,netdev=hN,mac=<MAC>,romfile=` (tote Hubs).
  `restrict=on`: DHCP auf ether1 kommt trotzdem, der Gast erreicht weder Container noch Internet.
  Gegenstelle und DHCP-Bereich müssen in `/ip service www available-from` liegen.
- **WebFig-Weg:** QEMU-`hostfwd` auf `0.0.0.0:<port>` ist aus anderen Containern NICHT erreichbar
  (Timeout). Belegt: Monitor `hostfwd_add mg tcp:127.0.0.1:8080-<Zugangs-IP>:<www-Port>` plus Relay im
  Container `0.0.0.0:80 → 127.0.0.1:8080` (Python asyncio im selben Prozess). Zweiter Container im
  Netz: `http://unifi-vorschau-chr-<id>:80/` → 200 `<title>RouterOS</title>`, REST `/rest/system/identity` 200.
- **WAN/Remote-Variante:** nach dem LAN-Lauf QEMU per Monitor `quit`, dieselbe qcow2 neu starten,
  Verwaltungs-NIC mit der MAC des Uplink-Ports (DHCP-Client-Schnittstelle), slirp-Netz aus
  `available-from` (z. B. 192.168.2.0/23), `restrict=on`; die alte Verwaltungs-NIC wird toter Hub.
  Lease nach ~3 s, WebFig/REST 200. Belegt in zwei Läufen. In Stufe 1 nur `modus:'wan'` mit leerem
  Feld (DHCP), keine feste WAN-Adresse.

## 6. Zustandsmaschine des Laufs (Backend `server/arten/mikrotik.js`, Container `chr_lauf.py`)
1. `vorbereiten` (Backend): Magic lesen (`0xB1A1AC88` Klartext; verschlüsselt → 400), `.rsc`: erste
   Zeile `# … by RouterOS x.y.z`; Optionen prüfen; Version wählen (`waehleChrVersion`); Wegwerfpasswort
   erzeugen (`.rsc`: Zugang `admin` + Wegwerfpasswort).
2. `laden` (Backend): `imageInfo(CHR_IMAGE)` sonst „Vorschau-Image fehlt – ./manage.sh rebuild“;
   `/cache/chr-<v>.img` vorhanden? sonst Download `…/chr-<v>.img.zip` als Strom nach `.chr-<v>.zip.teil`
   (Fortschritt), fflate-Unzip streamend nach `.chr-<v>.img.teil`, atomar umbenennen; 404 →
   „RouterOS <v> gibt es nicht bei MikroTik“; `.teil`-Reste erst hier (lazy) löschen, nie beim
   Modul-Import. Netz sicherstellen, Volume sicherstellen.
3. `starten`: Container erstellen (KVM-Rückfall), Tar hochladen, starten, `logsFolgen`. Container:
   FAT-Image bauen, QEMU-Start → `Login:` (Limit 120 s, real 4 s) → Login `admin` leer `+ct999w`,
   Lizenzfrage `n`, Passwortpflicht → Wegwerfpasswort → Prompt (real 17 s) → `/ip address print terse`
   zeigt DHCP auf ether1, sonst statisch `dhcpstart/prefix` setzen.
4. `einspielen`: `.backup`: `/system backup load name=pcie1/kunde.backup password=""` → `[y/N]` binnen 30 s
   → `y` → `Login:` (Limit 300 s, real 5 s); `Failed to restore … failure: …` = Fehler mit Routertext.
   `.rsc`: vorher `/ip dhcp-client remove [find]`, dann `/import file-name=pcie1/kunde.rsc` ohne
   Neustart; `Script Error … (line N)` = Fehler mit der Zeile N aus der Datei.
5. `anmelden`: Login `benutzer`/`passwort` (Passwortpflicht → Ctrl-C); `Login failed` → „Zugang
   <benutzer> abgelehnt – Standard-Zugang MikroTik prüfen“. Bis 30 s auf `[:len [/interface ethernet find]]`
   == NIC-Zahl warten; fehlt eine → nur Hinweis „Schnittstelle(n) fehlen nach dem Restore (RouterOS-Eigenheit,
   meist deaktivierte SFP-Ports)“, **kein automatischer Reboot** (nur wenn der Träger der Zugangs-IP
   fehlt, ein `/system reboot`-Versuch). `/system scheduler disable [find]; /system script job remove [find]`
   (Hinweis „Scheduler/Skripte angehalten“). Daten: `/system identity`, `/system resource print`,
   `/ip service print terse` (www-Port, aktiv, `available-from`), `/ip address print terse`.
   Träger der Zugangs-IP: Bridge → `/interface bridge port add bridge=… interface=[/interface ethernet get
   [find mac-address=02:FA:48:00:00:01] name] comment="FAH-Vorschau Zugang"`; Ethernet → Neustart-Variante
   (QEMU `quit`, Verwaltungs-NIC = MAC des Trägers an dessen PCI-Position); VLAN-Interface →
   `FAH-FEHLER Zugangs-Adresse liegt auf einem VLAN – anderen Zugangsweg (Bridge-Adresse) wählen`.
   WAN per DHCP → bis 60 s auf Lease warten. Dann `hostfwd_add` + Relay und `GET http://127.0.0.1:80/`
   bis 200 mit „RouterOS“ (Limit 30 s, real 8–19 s wegen RSTP). Rückfälle der Reihe nach: Firewall-Regel
   `chain=input in-interface=<Verwaltung> action=accept comment="FAH-Vorschau Zugang" place-before=0`
   (ohne `place-before` bei leerer Liste) → `/ip service set www disabled=no address=""` → Fehler
   „WebFig nicht erreichbar (Hotspot-Netz? anderen Zugangsweg wählen)“. REST-Probe
   `GET /rest/system/identity` (Basic-Auth) → `FAH-INFO {…}` → `FAH-BEREIT` → Skript bleibt laufen
   (`while qemu lebt: sleep 5`), SIGTERM → Monitor `quit`.
6. `bereit` (Backend nach eigenem `GET http://<chr>:80/webfig/` = 200): `bereitSeit`,
   `zugang = {benutzer, passwort, hinweis:'WebFig fragt nach der Anmeldung.'}`.

Fehlerfälle: Container endet (QEMU-Absturz) → `bisBereit` erkennt den Exit-Code → `scheitern` mit den
letzten Log-Zeilen; Abbruch durch Benutzer → `pruefe()` wirft `abgebrochen` → nur aufräumen; Wächter:
Leerlauf 30 min, Höchstdauer 8 h, Container nicht mehr `Running` → `fehler`. Alle Container tragen das
bekannte Label → Backend-Start und `manage.sh down` räumen sie weg. Jeder Teilschritt hat ein
Zeitlimit, Gesamtlimit 600 s (ohne KVM ×3).

## 7. Frontend (Kurzfassung)
- `#kacheln` (A–Z: Aruba, Barracuda, Fortinet, MikroTik, Omada, Securepoint, UniFi; aktiv MikroTik +
  UniFi, Rest „in Vorbereitung“ mit Einzeiler) → `#drop` je Art → `#workspace`. `#vorschau-leiste`
  zeigt den laufenden Lauf in der Übersicht. Knopf „Zur Übersicht“ in aside und `#drop`.
- MikroTik-Ansichten: Übersicht, Virtualisieren (Dialogkarte), Baum (`showMongo`-Muster: Rubrikliste
  mit Suche, Datensätze als `<details>` mit Feldtabelle + Hex, Volltext, JSON-Export), Rohdatei (Hex).
  UniFi bekommt den Hex-Block je Dokument dazu (`rawCollections`).
- Dialog: Erkannt-Zeile, Select CHR-Version (Kanäle, Cache, „andere Version …“ mit Prüfung, `hinweis`
  darunter), Radio Lokal (Select aus `backup.adressen`, Hotspot-Adressen markiert und nie vorgewählt)
  / WAN (nur DHCP), Benutzer/Passwort (Vorbelegung aus `vorbereitung.zugang`, nie getippte Werte
  überschreiben), bei verschlüsseltem Backup `.notice` mit `dont-encrypt=yes`, bei RouterOS 6 Hinweis
  „Virtualisierung folgt“, bei `.rsc` Beta-Hinweis. Jede Einstellung mit `.feld-hilfe`.
- Fenster `#vorschau-fenster` außerhalb von `#vorschau-inhalt` (sonst lädt der Frame bei jedem Poll
  neu): Kopf mit Titel, Status/Zugang, „Neuer Tab“, „Neu laden“, „Schließen“, „Beenden“ (zwei
  Klicks); schließt sich bei `!aktiv`, `fehler` und beim ersten Polling-401 vor `zurAnmeldung()`.
  Kopierknöpfe nur mit `navigator.clipboard` im sicheren Kontext.

## 8. Sicherheit
- Kein LAN/Internet für den Gast (`Internal`-Netz, `restrict=on`, tote Hubs). Der WebFig-Port ist nur
  im Docker-Netz `unifi-vorschau` erreichbar; nach außen nur über den angemeldeten Proxy.
- Geheimnisse nie in Env/Labels/Logs: `auftrag.json` wird nach dem Lesen gelöscht, Konsolenprotokoll
  maskiert (`password=`, `secret=`, `key=`, alle Passwörter des Auftrags), `FAH-*`-Zeilen ohne Geheimnisse.
- Ein `.backup` enthält Klartext-Geheimnisse; sie liegen im Browser, im Backend-RAM (Request-Body)
  und in der Schreibschicht des Containers unter `/volume3/@docker/overlay2` – beim Entfernen nur
  unlinkt, nicht gewischt.
- Standard-Zugang MikroTik: Klartext in `daten/einstellungen.json` (ACL auf `/volume3/docker` macht es
  NAS-weit lesbar) und für jedes angemeldete Konto abrufbar – bewusste Betreiber-Entscheidung;
  Minimum: nie in Logs, nicht in `andere`/`kurz`, nicht in Fehlertexten.
- iframe: Same-Origin, `frame-ancestors 'self'` auf Proxy-Antworten; `X-Explorer` schützt nur
  `/_explorer/api/*`, nicht die Proxy-Pfade (war bei UniFi schon so); `/rest` nutzt Basic-Auth,
  der Browser cached sie je Origin – betrifft nur die Wegwerf-VM.
- Docker-Socket + `/dev/kvm`: Das Backend reicht Geräte in selbst erzeugte Container (Root-Äquivalent
  bestand schon) – sicher nur, solange keine Nutzereingabe in `containerErstellen` landet.

## 9. Fallen (aus den NAS-Versuchen vom 10.10.)
1. Versionsabfrage: `upgrade.mikrotik.com/routeros/NEWEST7.stable` liefert veraltet `7.12.1` – richtig sind
   die „a“-Endpunkte `NEWESTa7.stable` (`7.24.5 1790691687`), `NEWESTa7.long-term` (7.23.8),
   `NEWESTa7.testing` (7.25rc1), `NEWESTa7.development` (7.26beta1), `NEWESTa6.long-term` (6.49.23);
   Format `<version> <unixzeit>`. Download `https://download.mikrotik.com/routeros/<v>/chr-<v>.img.zip`
   (7.24.5: 45,3 MB; unbekannte Version → 404).
2. `Login:` erscheint nach 4 s, das System ist aber erst ~15 s später benutzbar; direkt nach dem
   Restore-Neustart fehlen die Ethernet-Schnittstellen noch 0–3 s → immer auf die Anzahl warten.
3. In 3 von 8 (und erneut 1 von 2) Restores fehlte danach zufällig einer der deaktivierten SFP-Ports
   (Bridge-Port `interface=*12`) – nicht reproduzierbar, WebFig ging trotzdem → Hinweis, kein Reboot.
4. Schnittstellen werden per MAC zugeordnet; die Verwaltungs-NIC bekommt den ersten freien Namen
   (`ether17`, default-name `ether1`) → nie über Namen, immer `/interface ethernet find mac-address=`
   (`/interface find mac-address=` trifft auch die Bridge mit admin-mac → „invalid internal item number“).
5. Konsole: Enter als `\r` senden (7.16.2 ignoriert `\n` am Passwort-Prompt); `repeat new password>`
   enthält `new password>` (Lookbehind); Prompts werden mehrfach gezeichnet → vor Befehlen mit
   Rückfrage Puffer leeren; Login-Option `e` (dumb) füllt Zeilen mit 999 Leerzeichen, `+ct999w` liefert
   nur `ESC[9999B`-Sequenzen; `-serial stdio` braucht `signal=off`; Endmarke folgt bei Befehlen ohne
   Ausgabe direkt auf die Anfangsmarke (`(?<![^\r\n])`); Befehle immer als
   `:put "FAH<A n>"; :onerror fehler in={…} do={:put "FAH-FEHLER $fehler"}; :put "FAH<E n>"`
   (`:onerror` gibt es erst in RouterOS 7 – ein Grund für die v6-Sperre).
6. Dienst-Ports stehen nicht fest (Testbackup: www 5999, ssh 4444); `available-from` beschränkt auf
   feste Netze → slirp-Gegenstelle muss darin liegen; www-ssl mit Kundenzertifikat nur TLS 1.2.
7. SSH mit Passwort scheitert (`Permission denied (publickey)` – admin hat einen SSH-Schlüssel) →
   Konsole + REST sind die Steuerwege, nicht SSH.
8. Hotspot-Netze: dynamische `hs-input`/`hs-unauth`-Regeln (tcp-reset) liegen vor jeder statischen
   Regel; `place-before=0` und www-Freigabe helfen nicht → nie als Zugangsweg.
9. Kundenskripte laufen in der Vorschau (Scheduler `startup`, 1-/5-min-Intervalle), scheitern teils
   (`bad command name routerboard`, `/interface/ethernet/get no such item`) und ändern Konfiguration
   (WireGuard aus, Route/NAT deaktiviert); mit WAN-Lease CPU ~50 %. Ohne Netzabschottung würden sie
   Betreiber-APIs/DDNS wirklich erreichen.
10. `/file print terse where name=…` findet auf 7.16.2 die Datei nicht (kosmetisch; `backup load`
    meldet „file not found“ selbst). Export enthält nie `/user`.
11. QEMU-Monitor (HMP) wiederholt die Eingabe zeichenweise mit ESC-Sequenzen → nur die letzte Zeile
    auswerten; `hostfwd_add` erst nach dem Bridge-Port, ARP/RSTP brauchen ~8 s.
12. Warnungen „hub N is not connected to host network“ sind harmlos (gewollt tote Ports); 18
    slirp-Instanzen mit `restrict=on` würden stattdessen DHCP an Kundenports beantworten.
13. Volume `fah-chr-cache` existierte auf dem NAS schon ohne Compose-Label → in Compose `external: true`,
    `manage.sh` legt es idempotent an; Compose v5.1.3 verweigert sonst `up`.
14. RAM 256 MB reicht (frei 26–39 MiB), 384 MB bequem; CPU nach Restore kurz 88 %, dann 2 %.
    Zeiten (KVM, 7.24.5): Boot 4 s, Erstlogin 17 s, Restore→Login 5 s, Kundenlogin 1 s,
    Bridge-Port→WebFig 8–19 s, gesamt ~42 s; FAT-Weg bis Kundenlogin 28 s.

## 10. Deploy
`manage.sh update`: ZIP entpacken → Dateien ins Root → `docker build -f chr/Dockerfile.chr -t fah-extraktor-chr chr/`
→ `compose build --no-cache` → Volume `fah-chr-cache` sicherstellen → `up --force-recreate`. Scheitert
ein Bau, läuft die alte Version weiter. Update, `down` und Backend-Neustart beenden alle Vorschauen.
Erster Deploy nach der Umbenennung: `DEPLOY_GLOB="fah-extraktor*.zip" nohup ./manage.sh update`.
